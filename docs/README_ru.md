# rag-lab

[![CI](https://github.com/rikitikitav1/rag-lab/actions/workflows/ci.yml/badge.svg)](https://github.com/rikitikitav1/rag-lab/actions/workflows/ci.yml)

RAG-система над личной базой знаний и внешними IT-репозиториями. Отвечает на технические вопросы и возвращает источники, использованные как контекст. Ретривал собран **из примитивов**: гибрид возвращает ранг каждой ноги, и на этих рангах стоит гейт слабого ретривала, а библиотечный ретривер отдаёт наружу список документов. Там, где стандарт просто лучше, он и берётся: агент работает на **LangGraph**, а markdown разбирает `MarkdownHeaderTextSplitter`, который отличает заголовок от комментария внутри блока кода (наш регэксп не отличал). Агент начинался самописным, и перенос замерен против оригинала до того, как оригинал убрали (см. [запись](experiments/2026-08-26_the-same-agent-written-four-ways.md)). Инференс **локальный** (Ollama на своей GPU).

Это **витрина-лаборатория**: стенд, чтобы руками отрабатывать инженерные подходы LLM/RAG (retrieval, eval на LLM-судье, lifecycle моделей, reranking, async-очереди) и показывать результат на цифрах. Не продакшн-сервис, а полигон подходов.

## Что это

- **Варианты корпуса**: несколько нарезок живут в базе одновременно, у каждой свой частичный векторный индекс и своя политика в снапшоте прогона. Переиндексация перестаёт быть границей несравнимости и становится обычным свипаемым параметром ([запись](experiments/2026-08-26_a-corpus-you-can-keep-two-of.md)).
- **Гибридный retrieval**: векторный поиск (pgvector) + полнотекстовый (Postgres FTS с per-language стеммингом), слияние через **RRF** (Reciprocal Rank Fusion). Фильтр по иерархическим категориям (ltree), distance-порог с честным отказом на вопросах вне корпуса.
- **Локальные модели** через Ollama по ролям: генерация, эмбеддинги (`bge-m3`), LLM-судья. Роль отвязана от конкретной модели: какая модель обслуживает роль, хранится в БД и меняется на лету.
- **Мультиисточник**, единая таксономия: личные заметки (rus), 173 interview-репозитория Devinterview-io (eng) и три документационных источника со своими правилами: `system-design-primer`, `redis-doc` (заголовок во frontmatter) и `cheatsheets` (frontmatter плюс пофайловые правила выброса мусора). Стратегия ingestion объявляется политикой, а не зашивается в резчик.
- **Eval-стенд, 5 осей качества**: retrieval (hit@k / MRR), faithfulness (грунтован ли ответ в контексте), relevance (отвечает ли по существу), completeness (покрывает ли эталонный ответ), refusal-accuracy - через **LLM-as-judge** со structured output. Оценки считаются по пулам отдельно: ответы из корпуса, ответы из внешнего тула (`remote_grounding` меряет обоснованность текстом тула, а не правоту самого тула) и отказы, рядом с долей отвеченного и долей ответов вообще без опоры. У каждого вопроса в ране пишется исход (`answered`, `refused`, `unsupported_answer`, `narrated_call`, `exhausted`, `error`): если считать ответ без источников отказом, выигрывает ровно та политика, которую меряем.
- **Асинхронный job-queue**: тяжёлые операции (pull/delete моделей, индексация корпуса, эмбеддинг банка вопросов) уходят в очередь на Postgres, их разбирает воркер. Сервис зависит только от Postgres: Ollama может быть недоступна на старте, джобы дефёрятся/ретраятся, приложение не падает.
- **Reranking, выключен по умолчанию с 30.08 и померен в обе стороны**: cross-encoder `bge-reranker-v2-m3` поверх гибрида (retrieve-wide → rerank → narrow). Он был дефолтом, пока не выяснилось, что агентному пути нужен генератор с tool calling: 8b, у которой он есть, забирает ту память карты, которую держал реранкер. Теперь его **включает** запрос или прогон. Измеренная польза не изменилась, дефолт это решение про карту, а не вердикт методу. На уровне ранжирования улики спорят между собой: на 823 кросс-язычных вопросах он стоит **+0.0369 MRR по разделу** [0.0155, 0.0596], а на 820 одноязычных **−0.0245** [−0.0460, −0.0021], и оба интервала не задевают ноль. На уровне ответа для генератора, который мы подаём, вреда нет: `gemma3:4b` с реранком против без даёт релевантность **+0.324** [0.111, 0.530] и полноту **+0.277** [0.111, 0.433] на русском наборе и три интервала через ноль на английском. Цена на карте: 168 мс на вопрос в фазовом прогоне против 2.76 с на процессоре.
- **Агент на LangGraph**: tool-calling граф, где модель сама решает когда искать по корпусу, может переформулировать запрос и сделать несколько хопов, затем отвечает. Начинался как рукописный цикл, и цикл убрали только после того, как перенос совпал с ним в пределах собственного шума стенда. Политики вокруг цикла (гейт покрытия, ось темы, допуск инструментов) остались нашими и измерены, а не приняты на веру. Выбирается как eval-пайплайн (`pipeline: agent`) и меряется в лоб против single-shot RAG (см. лог экспериментов).
- **Route-driven eval-платформа**: генерация не-циркулярных наборов (LLM-парафраз interview-вопросов + перевод на ru), импорт вопросов файлом, прогоны и оценка судьёй - всё булково через очередь; наблюдаемость через лог запросов (`question-log`) и джобы с `elapsed`.
- **Слоёвка**: транспортно-нейтральные `use_cases` → тонкие адаптеры (CLI / FastAPI REST).

## Стек

Python · PostgreSQL + pgvector · SQLAlchemy 2.0 (sync psycopg + async asyncpg) · Ollama (GPU, OpenAI-совместимый API) · FastAPI · dbmate (миграции) · uv/pyproject · Docker Compose.

Из семейства LangChain ровно три пакета и больше ничего: **langgraph** исполняет агента как `StateGraph`, **langchain** даёт `create_agent` для руки, которая отвечает на вопрос «сколько стоит идиоматичная версия», **langchain-text-splitters** решает, что считать заголовком markdown. Ретривал, очередь, eval-стенд и политики корпуса наши; версия сплиттера едет в отчёте о нарезке, потому что разбор теперь внешний код, и обновление lock-файла иначе сдвинуло бы нарезку молча.

## Архитектура моделей и промптов

- **Model / ModelRole**: `Model` (имя + статус: available/loading/ready), `ModelRole` (role как PK → одна модель на роль по построению, FK `ON DELETE RESTRICT` = БД не даст удалить назначенную модель). `Role` это замкнутое множество из четырёх: `generation`, `embedding`, `judging`, `paraphrasing`. Резолвер `llm.resolve_name(role)` берёт имя из БД, а параметры инференса из `config.yaml`: файл объявляет модель роли, служит база. `llm.candidates` называет модели, которые качаем, но не назначаем.
- **Имя модели проверяется одинаково на обеих дверях**: `MODEL_NAME_RE` на форму, 128 символов на длину, а трёхсегментное имя может указывать только на `hf.co` или `registry.ollama.ai`. HTTP-дверь и джоба, регистрирующая модель по имени, зовут одну функцию: имя, доехавшее до pull второй дверью, раньше проходило мимо правил первой.
- **Purpose**: их одиннадцать, и промпт принадлежит ровно одному. Одно на ответ (`generate.answer`), три судейских, три на сборку наборов вопросов (`paraphrase.question`, `translate.question`, `question.from_heading`), четыре агентных (`agent.system`, `agent.fallback`, `agent.tool_match`, `agent.no_evidence`).
- **Pipeline**: `single_shot` или `agent`, пишется в `question_logs.pipeline` на каждый ответ. Два пути требуют от одной роли генерации разного, поэтому модель может годиться для одного и не годиться для другого.
- **Prompt**: версионирование в БД (`purpose` + `version`, ровно один `active` на назначение). Исходники лежат файлами в `prompts/` и названы по имени члена enum, а не по строке назначения (`agent_fallback.v1.txt` несёт назначение `agent.fallback`). Сид заливает их в БД, и новая версия становится активной, **только если у назначения активной ещё нет**; иначе она ложится неактивной с предупреждением, а переключает её осознанный шаг `POST /v1/prompt/{id}/activate`.
- **Bench**: чем на самом деле судила одна проходка, объектом, а не допущением: модель плюс прибитая версия промпта на каждую ось. Живой путь берёт активные версии, у руки пересуда свои, и именно так две руки осознанно судят одни и те же ответы по-разному.
- **Что прогон записывает про свои инструменты**: `question_logs.models` и `question_logs.prompts`, которые заполняет отвечающий путь, а судья дописывает туда свою модель и версии `judge_*`. Рука говорит, что заказали, эти две колонки говорят, что отработало, и на пересуде эта разница и есть весь замер.
- **Реранкер не входит в роли**: кросс-энкодер не в ollama и не в `llm.roles`, он грузится в процессе из `service.rerank`, и проверки резидентности, которые спрашивают ollama, его не видят.
- **Что роль требует от модели** (tool calling у генератора агента, судья без рассуждений по умолчанию, арифметика карты и то, почему имя модели роли служит из базы, а не из файла): [model_requirements.md](model_requirements.md).
- **Bootstrap** (одноразовый сервис compose, idempotent): завести Model-строки из конфига → засидить роли → сверить с Ollama (что не скачано → статус `loading` + джоба pull) → заэнкьюить индексацию, только если в базе нет ни одного варианта корпуса → построить частичный векторный индекс каждому варианту, у которого есть строки и нет индекса → починить индекс обслуживаемого варианта, если он пропал → заэнкьюить эмбеддинг вопросов без вектора, если такая джоба ещё не стоит. Названный, но пустой вариант пишется в лог, а не индексируется: индексация варианта это осознанный измеряемый шаг.

## Конфигурация

Всё тюнингуемое вынесено в **`config.yaml`** (монтируется в контейнер):

- `llm.roles` - модель + `options` на каждую роль (`generation` / `embedding` / `judging` / `paraphrasing`); имя здесь это то, что bootstrap назначит на пустой базе, дальше служит база. `llm.candidates` - модели, которые тоже скачать, но не назначить. `llm.context_length` - каким мы ждём `OLLAMA_CONTEXT_LENGTH`, preflight сверяет с сервером. `llm.base_url` - где слушает ollama.
- `service.retrieval` - `distance_threshold`, `results_limit`, `rrf_k`, лимиты кандидатов и тумблеры ключевой ноги: `keyword_query` (`and` требует все лексемы, `or` срабатывает на любую), `keyword_rank`, `keyword_norm`, `query_lang` (по умолчанию `function_words`, ещё `langdetect` и `cyrillic_ratio`), и глубина векторного индекса: `ef_search` (прибит к 100, см. ниже) плюс лестница, из которой он выбирается, и ворота, которыми он судится (`ef_ladder`, `recall_gate`, `max_mrr_loss`, `max_questions_lost`), плюс дымовой тест preflight, который говорит только «индекс жив» (`index_alive_recall`, `index_alive_questions`). `criterion_sets` и `veto_sets` называют наборы, на которых читается вердикт, и набор, который умеет только вето. Значения выбраны замером и пишутся в снапшот каждого прогона.
- `service.rerank` - `enabled` (выключен с 30.08, см. выше; запрос или прогон может включить), `model`, `candidates`.
- `service.agent` - `max_hops` (кап хопов агента), `fallback_policy` (`corpus_first` / `corpus_first_weak` / `agent_choice`), `gate_signal` (что считает ретривал слабым: `distance`, `cross_encoder` или `either`) с порогами `weak_distance` и `weak_threshold`, `gate_candidates` (сколько результатов скорит кросс-энкодер), `topic_threshold` (ось темы: расстояние до ближайшего чанка, выше которого прогон отказывается вместо похода наружу; одно число или по одному на язык, ноль в прогоне её выключает).
- `service.ingestion` - `batch_size`, `commit_size` и `chunk_max_size` как запасной потолок для источника без политики варианта (сама нарезка читает `max_chunk_size` варианта).
- `service.fts` - text-search конфиг на язык и фолбэк. Это индексное: смена переиндексирует корпус, а не переранжирует запрос.
- `repos_dir`, `prompts_dir` - откуда читаются склонированные источники и файлы промптов.
- `service.ingest_quality` - что делает источник сломанным, а что просто грязным: `hard_gates` и `soft_gates` в долях чанков источника, `weights` для балла 0-100, сколько истории хранить на вариант, и `score_formula`, которая пишется в каждый отчёт, чтобы балл по другой формуле не читали как этот. Пороги поставлены от измеренного по корпусу, и рядом с каждым написано, что он читает сегодня.
- `service.corpus` - `description`, `variant` (какой вариант корпуса читается по умолчанию) и `variants` (политика нарезки каждого, попадает в снапшот прогона).
- `service.sources` - источники (interview-репозитории и их base_url).
- `postgres` - подключение к БД.

В коде остаются source-специфичные деревья категорий.

## Быстрый старт

```bash
docker compose up -d
curl localhost:8000/readiness            # pg обязателен, ollama мягко
curl -X POST localhost:8000/v1/chat/question \
  -H 'Content-Type: application/json' -d '{"text": "What is a hash table?"}'
# Swagger: http://localhost:8000/docs
```

Аутентификации нет намеренно (REST, `/mcp`, `/mcp-ops` открыты): это локальная лаборатория, порты привязаны к 127.0.0.1. Не выставляйте её в сеть как есть.

Первый `up` тянет ~16 ГБ моделей и строит индекс (~5-10 мин, следи за `docker compose logs -f worker`). Сервер дожидается завершения `bootstrap` и healthy-статуса ollama, и это и есть основная задержка; скачивания и индексации, которые те шаги ставят в очередь, он **не** ждёт, поэтому первые запросы могут вернуть отказ, пока корпус наполняется.

Сценарии на руках (мини-eval до чисел, A/B реранка, импорт своих вопросов, чтение логов): **[use_cases.md](use_cases.md)**. Это девять сценариев, а не индекс роутов; полный справочник это Swagger на `/docs`, он генерируется из кода и отстать от него не может.

## Сервисы compose

| Сервис | Роль |
|--------|------|
| `postgresql` | Postgres + pgvector, единственная жёсткая зависимость |
| `dbmate` | накатывает миграции, отрабатывает до старта остальных |
| `seed` | заливает промпты и банк вопросов, отрабатывает один раз после миграций |
| `bootstrap` | готовит модели, роли и джобы индексации, отрабатывает до старта остальных |
| `rag-lab` | FastAPI-сервер (uvicorn) |
| `worker` | разбирает job-queue, двенадцать типов: pull/delete модели, индексация корпуса, сборка векторного индекса, анализ источника, эмбеддинг вопросов, парафраз вопросов, сборка набора-вето, прогон, судейство, сравнение ретривала, mcp-health |
| `ollama` | локальный инференс на GPU |

### Переменные окружения

Весь тюнинг пайплайна живёт в `config.yaml`; в окружении остаётся только то, что зависит от машины или не должно попадать в репозиторий. Скопируйте `.env.example` в `.env`: compose подхватит его сам, у каждого значения есть рабочий дефолт.

| Переменная | Дефолт | Что делает |
|------------|--------|------------|
| `RERANK_DEVICE` | `cuda` | Где считает кросс-энкодер для API. Compose задаёт его там, а воркеру отдаёт `WORKER_RERANK_DEVICE`, поэтому задавать эту переменную в `.env` бесполезно; она в таблице только потому, что код её читает. Из-за карты дефолт и переехал: `bge-m3` 851 MiB, `bge-reranker-v2-m3` 1728 MiB по замеру и `gemma3:4b` 4248 MiB в 8188 MiB помещаются, а `llama3.1:8b` вместо 4b уже нет, и агентному пути она нужна, потому что у gemma3 нет tool calling вовсе. Поэтому реранк выключен по умолчанию и запрашивается на прогон. |
| `LLM_TIMEOUT` | `120` | Секунд на один ответ модели. 70b на CPU думает минутами, дефолт убивает такие прогоны на полпути. |
| `WORKER_RERANK_DEVICE` | `cuda` | Где воркер считает кросс-энкодер. Фазовый прогон реранкает батчем, владея картой, а гейт corpus-first скорит несколько пар на вопрос. Ставить `cpu` стоит только когда карта нужна целиком чему-то другому. |
| `OLLAMA_CONTEXT_LENGTH` | `8192` | Окно контекста, с которым сервер грузит модели. Дефолт Ollama это 4096, и чтобы влезть, он молча выбрасывает целые сообщения, поэтому слишком длинный промпт никогда не виден как число больше окна; самый длинный хоп в логах 4075 токенов. Рост окна стоит видеопамяти, которую делит эмбеддер: при 14336 они выгружают друг друга на каждом переключении. После изменения смотри `llm.model_spilled_to_cpu`; в снапшот пишется окно, которое отдаёт сервер, а не это значение. |
| `WORKER_QUEUES` | `default,io` | Лейны очереди, которые обслуживает воркер, по треду на каждый. Сетевые и дисковые джобы (скачивание моделей, health MCP) живут в `io` и не ждут за GPU-работой. |
| `HF_TOKEN`, `CONTEXT7_API_KEY` | пусто | Секреты внешних MCP-интеграций. Читаются только переменные из allowlist в `config.yaml` (`mcp_integrations.secret_env`). |

## REST API

Полный интерактивный справочник в Swagger: `/docs`.

Листинговые эндпоинты (`/v1/model`, `/v1/prompt`, `/v1/job`, `/v1/question-log`) используют общую пагинацию: `limit` (по умолчанию 100, максимум 1000), `offset`, `sort_by`, `sort_order` (`asc`/`desc`, по умолчанию `desc`).

Health:
- `GET /liveness`, `GET /readiness`

Чат и поиск:
- `POST /v1/chat/question` (полный RAG-ответ; опц. флаг `rerank`; опц. override языка `language` `ru`/`en`)
- `POST /v1/chat/fast_question` (только retrieval, без генерации)

Отдельный прогон идёт не циклом по вопросам, а фазами: каждая стадия владеет картой одна, за счёт чего реранк на большом сете становится по карману. Фазы стоят нескольких подкачек модели за прогон вместо двух на вопрос, и прогон отдаёт карту, когда заканчивается, поэтому очередь прогонов на разных генераторах не держит на карте сразу два. Реранкер наконец получает настоящий батч: 31 с на 100 вопросов на карте против примерно 16 минут на процессоре. Эти 310 мс на вопрос это вся фаза, вместе с загрузкой модели и поиском; сам реранк стоит 86 мс, померенных в `datasets/measurements/rerank_latency.json`.

Эксперименты (полноценная сущность над сырым роутом серии):
- `POST /v1/experiment` (создаёт эксперимент - dataset + детерминированная выборка по seed / снапшот процедуры / варьируемый параметр - и ставит серию прогонов), `GET /v1/experiment` (список с фильтрами), `GET /v1/experiment/{id}`, `PUT /v1/experiment/{id}/conclusion`, `POST /v1/experiment/{id}/arms` (только для пересуда: копирует ещё руки тех же ответов и пересуживает их, из `aggregated` обратно в `running`; руки называются поимённо, а не сеткой, и кап строк считает уже имеющиеся)
- стейт-машина `draft → running → aggregated → concluded` (+ `failed`); после последней judge-джобы серии агрегатор считает метрики по каждому значению + RRF-композит по пяти осям (три судейские, доля отказов на внекорпусных и доля подкреплённых ответов) и пишет в `results` (retrieval hit@k/MRR отдаются per value, но в фьюжен не входят: hit@k монотонен по `k` и конфаундил бы композит)
- в results лежат **парные статистики значимости**, а не только точечные оценки: для победителя против каждого другого значения, по осям - средняя парная дельта (один и тот же вопрос в обоих прогонах), bootstrap 95% CI и p-value Уилкоксона, плюс флаги значимости с поправкой Бонферрони на всё семейство тестов - JSON сам говорит, что пережило поправку на множественные сравнения

Один вызов = один вопрос стенду; генерация, судейство и агрегация происходят в фоне. Вопросы, которые так можно задавать:

```bash
# "Сколько чанков кормить генератору?" - свип ширины ретривала
curl -sX POST localhost:8000/v1/experiment -H 'Content-Type: application/json' -d '{
  "name": "k_sweep", "dataset": "paraphrased_ru", "sample_size": 100,
  "pipeline": "agent", "language": "ru", "param": "k", "param_values": [1, 3, 5, 7, 10]}'

# "Окупает ли себя модель побольше на моём корпусе?" - A/B моделей
# (модели, которой нет в реестре, скачается автоматически, прогон подождёт)
curl -sX POST localhost:8000/v1/experiment -H 'Content-Type: application/json' -d '{
  "name": "model_ab", "dataset": "paraphrased_ru", "sample_size": 100,
  "param": "model", "param_values": ["llama3.1:8b", "gemma2:9b"]}'

# "Дают ли что-то лишние хопы агента?" - свип капа хопов на дешёвой выборке из 10 вопросов
curl -sX POST localhost:8000/v1/experiment -H 'Content-Type: application/json' -d '{
  "name": "hops", "dataset": "paraphrased_ru", "sample_size": 10, "sample_seed": 42,
  "pipeline": "agent", "param": "max_hops", "param_values": [2, 4, 6]}'

# «Судья читает ответ или самого себя?» - пересуд: ответы держатся неподвижно, двигается
# только судья. Руки это копии одного записанного прогона, поэтому корпус, поиск и
# генератор различаться между ними не могут; оси только судейские (модель и версии трёх
# промптов) плюс `repeat`, который ничего не меняет и называет повтор. Дельта двух рук
# `repeat` это собственный шум судьи
curl -sX POST localhost:8000/v1/experiment -H 'Content-Type: application/json' -d '{
  "kind": "rejudge", "name": "judge_noise", "source_run": "grid_gemma3_4b_ru_plain",
  "param": "repeat", "axes": {"repeat": [1, 2]}}'
```

Пересуд отвечает на вопрос, который другим типам недоступен: сколько в разнице двух прогонов
было судьи, а не ответа. Ничего не генерируется, поэтому рука стоит одного судейского прохода
и ни минуты карты под генератор. В отчёте нет RRF-композита (ретривальные метрики у рук
одинаковы по построению), зато есть средние по руке, парные дельты на восьми
seed по всем парам, пока рук шесть или меньше, и первая против остальных, когда больше,
половины A/B и `answers_digest` у каждой руки рядом с дайджестом источника,
так что «руки судили одни и те же ответы» это факт записи, а не утверждение в её описании.

Пересудить один прогон, не заводя эксперимента: `POST /v1/eval/rejudge` с
`{"source": "<прогон>", "run_name": "<копия>"}` копирует ответы под новым именем с пустыми
вердиктами и ставит по ним судью.

Когда серия отсужена, `GET /v1/experiment/{id}` возвращает метрики по каждому значению и композитный вердикт:

```json
{
  "status": "aggregated",
  "results": {
    "per_value": {"5": {"faithfulness": 7.18, "relevance": 8.9, "completeness": 6.16, "hit_at_k": 0.9, "mrr": 0.757}, "...": "..."},
    "composite": {
      "method": "rrf", "winner": "5",
      "ranking": [{"value": "5", "rrf": 0.0487}, {"value": "10", "rrf": 0.0484}],
      "pairwise": {
        "comparisons": {"5_vs_10": {"faithfulness": {"mean_delta": 0.19, "ci95": [-0.17, 0.57], "p": 0.3669, "n": 100, "significant_raw": false, "significant_bonferroni": false}, "...": "..."}},
        "method": "bonferroni", "alpha": 0.05, "tests": 15, "threshold": 0.00333

  }
}
```

Блок pairwise - то, что держит выводы честными: ранняя версия стенда «заключила», что k=5 лучше k=10, по разнице композита в третьем знаке - парный тест показывает, что это сравнение монетка (p=0.37), а флаги с поправкой отмечают, какие из 15 тестов решётки вообще выживают. Случаи, где это развернуло наши собственные вердикты - в [experiments.md](experiments.md).

Перед сеткой `scripts/preflight_grid.py` отсекает способы тихо обессмыслить прогон: правленое
дерево, воркер на вчерашнем коде, модель, съехавшую на процессор, корпус, который больше не
нарезается в те строки, что лежат в таблице, глубину поиска, на которой планировщик уже перестал
ходить по индексу. `--verify` проверяет вместо стенда готовый прогон. Каждый из этих отказов даёт
законченный прогон с правдоподобными числами и без единой ошибки, и поэтому это не тест, а
проверка. Что именно отсекает каждая из шестнадцати и какой инцидент её породил:
[preflight.md](preflight.md).

Вывод фиксируется через `PUT /v1/experiment/{id}/conclusion`, и эксперимент становится самодостаточным артефактом: что варьировали, на каких данных, цифры, вердикт.

Наблюдаемость:
- `GET /v1/question-log`, `GET /v1/question-log/{id}` (логи ответов; фильтры вкл. `pipeline`, `faithfulness`/`relevance`/`completeness`, `run_name`; и по записанному снапшоту: `rerank`, `rerank_device`, `phased`, `empty_retrieval`, `max_distance`, `answered_via_remote`, так что «покажи все ответы, где корпус ничего не нашёл» это один запрос; детально с context)

- `POST /v1/job/cancel` (отменить сразу весь прогон или тип джоб: отмена по одному id через страничный листинг это ровно тот способ, которым «остановленный» eval продолжил считать)

## MCP

MCP-сервер (Model Context Protocol) примонтирован на `/mcp` (streamable HTTP) и отдаёт корпус любому MCP-клиенту (Claude Desktop, Cursor, IDE-агенты). Построен на standalone `fastmcp`, переиспользует те же примитивы поиска, что REST/agent. Тулы:
- `search_corpus(query, category?)` - гибридный поиск, отдаёт чанки с маркерами `[source]`; опц. фильтр по категории.
- `answer_question(text, pipeline?, category?, language?)` - полный RAG-ответ, возвращает `{answer, retrieved, sources}` (`agent` или `single_shot`; `category` только с `single_shot`).
- `list_categories(category?, only_top?)` - пути категорий с количеством чанков, для discovery валидных значений фильтра перед поиском.

Подключение: `claude mcp add --transport http rag-lab http://127.0.0.1:8000/mcp/`, или MCP Inspector на тот же URL.

Второй, отдельный ops-сервер примонтирован на `/mcp-ops` - control plane eval-платформы, вынесенный с продуктовой поверхности (внешний клиент получает search/answer, а не админские глаголы):
- `run_metrics(run_name)` - агрегированные метрики прогона (генеративные оси + retrieval hit@k/MRR).
- `compare_runs(run_names)` - сравнение прогонов бок о бок с RRF-композитным ранжированием (только генеративные оси).
- `compare_pools(run_names)` - те же прогоны в разбивке по пулам (in-corpus / out-of-corpus / off-domain) со срабатываниями гейта, латентностью, гистограммой исходов и парным тестом Уилкоксона на каждую пару прогонов.
- `list_jobs(status?, type?, run_name?)` / `cancel_job(id)` - управление очередью джоб, cancel снимает и зависимый judge.

### MCP-клиент: агент потребляет внешние серверы

Лаборатория теперь обе стороны протокола: свой MCP-сервер выше и MCP-*клиент* ниже. Внешние hosted-серверы регистрируются как `McpIntegration`, их тулы попадают в тулбокс агента рядом с `search_corpus` под неймспейсом `integration__tool` (например `deepwiki__ask_question`). Жизненный цикл через `/v1/mcp_integration`:

- `allowed_tools` - явный allowlist: discover показывает каталог, человек выбирает, что реально видит 8B-модель. Описания тулов обрезаются при кэшировании, результаты обрезаются до `max_result_chars`.

Про границы доверия: auth нет намеренно; любой с доступом к API может зарегистрировать интеграцию на произвольный url, и разрешённые секреты уйдут туда. Не выставляйте сервис наружу.

Сиды (все disabled до явного включения): DeepWiki (без auth), Hugging Face (`HF_TOKEN`), Context7 (`CONTEXT7_API_KEY`).

### Corpus-first: когда агенту можно наружу

Выдать 8B-модели тулбокс и надеяться, что она предпочтёт локальный корпус, это не политика. `fallback_policy` делает порядок явным и, что важнее, измеримым:

- `corpus_first` (дефолт) - ран стартует с одним `search_corpus`. Внешних тулов нет в схеме, и `dispatch` отказывает им по имени, так что придуманный вызов не утечёт наружу. Как только поиск по корпусу вернул пусто, удалённые схемы дописываются в тулбокс со следующего хопа, а в лог пишется `fallback_reason: empty`.
- `corpus_first_weak` - то же плюс гейт покрытия над тем, что всё-таки нашлось. Чем меряется слабость, решает `agent.gate_signal`: `distance` (по умолчанию) сравнивает векторную дистанцию лучшего результата с `agent.weak_distance`, `cross_encoder` скорит верхние `agent.gate_candidates` и сравнивает лучший с `agent.weak_threshold`, `either` открывается, когда слабость увидел хотя бы один из двух. Ниже планки ретривал считается промахом (`fallback_reason: weak`), а слабые чанки выбрасываются из диалога, а не идут в ответ, но только когда есть внешний тул, готовый подхватить. Кросс-энкодерной ветке не нужен включённый реранк: при `rerank: false` она скорит пять пар и не трогает порядок, при включённом переиспользует уже посчитанные скоры.
- `agent_choice` - всё видно с первого хопа (поведение до политики, оставлено бейзлайном для A/B).

Форсим ФАКТ обращения к корпусу, а не формулировку: переформулировка и решение идти наружу остаются за моделью, здесь 8B как раз неплоха (включая кросс-язычный поиск).

Но сначала тул должен заслужить место в тулбоксе: каждый внешний тул один раз за ран проверяется по вопросу, и тот, ради которого модели пришлось бы выдумать обязательный аргумент, не выдаётся вовсе. Без этой проверки корпусный вопрос про готовку уходил в репозиторный тул с выдуманным именем репозитория, и faithfulness по таким вопросам падал до нуля. Два более дешёвых роутера мерились раньше, оба провалились. Отказ в допуске ничего не стоит: передавать вопрос некому, значит ран вырождается в обычное корпусное поведение.

Когда не ответил ни один источник, ран больше не заканчивается молчанием: финальный ход идёт без тулов и несёт версионируемую инструкцию (`agent.no_evidence`) сказать прямо, что доступные источники вопрос не покрывают, и не отвечать по памяти. Такие раны возвращаются отказом на языке вопроса, а не пустым результатом.

Когда тулбокс открывается, модели об этом сообщают: версионируемое уведомление (промпт `agent.fallback`) дописывается в результат тула и перечисляет внешние тулы с их обязательными аргументами. Именно в результат тула, и это не косметика: `system`-сообщение в середине диалога ломает шаблон llama3.1 настолько, что модель начинает печатать вызовы прозой вместе с заголовком роли. Оттуда же ещё две страховки: на вызов без обязательных аргументов `dispatch` отвечает их перечислением (8B склонна переиспользовать форму аргументов предыдущего тула), а ход, который вместо вызова его пересказал, получает ровно одно напоминание сделать вызов по-настоящему.

Каждый отказ внешнего тула классифицируется на пути вызова (`timeout`, `connect`, `auth`, `client`, `server`, `tool`) и попадает в `metrics.tool_errors`: у видов разная политика деградации, `auth` значит ключ протух и ретраи бессмысленны, `tool` значит кривые аргументы, остальное транзиент. Две ловушки, найденные пробами по живым отказам: fastmcp прячет мёртвый хост под `RuntimeError`, а настоящий `httpx.ConnectError` лежит в `__cause__` внутри `ExceptionGroup` от TaskGroup; несуществующее имя тула возвращается серверным `ToolError`, а не транспортной ошибкой.

Политика и причина едут в снапшоте лога, поэтому прогоны до и после сравнимы, а `/v1/question-log?fallback_reason=empty` достаёт ровно те вопросы, которые корпус не обслужил.

Замерено на трёх пулах по сто вопросов. Правило пустоты срабатывает **ни разу**, потому что гибридный поиск всегда возвращает хоть что-то выше порога; гейт покрытия превращает это в 60 вопросов, ушедших наружу, и поднимает обоснованность на них с 2.31 до 5.08 (p<0.001), а корпусная половина не двигается. Приоритет корпуса бесплатен по качеству и не бесплатен по времени: около двух секунд на вопрос за гейт и ещё двенадцать за внешний хоп. Цифры и оговорки: [журнальная запись](experiments/2026-08-25_the-gate-that-fires-and-the-refusal-that.md).

Каким сигналом мерить слабость, решала отдельная сетка: три руки по 200 вопросов, одна переменная. Ни одна ось не отделяет `distance` от кросс-энкодера, а интервалы говорят, насколько сильно это можно утверждать (±0.8 балла в корпусе, ±1.5 снаружи), при этом `distance` на секунды дешевле, поэтому дефолт он. Кросс-энкодер из рантайма никуда не делся: `gate_signal: cross_encoder` работает. `either` покупает релевантность, а не обоснованность, и релевантность это ровно та ось, слепоту которой к галлюцинации показывает этот же замер, поэтому он остаётся измеренной опцией, а не дефолтом. Цифры и оговорки: [журнальная запись](experiments/2026-08-25_a-cheaper-gate-signal-and-a.md).

Тот же прогон говорит вещь куда менее приятную: **ни одна политика не отказывается.** На сотне вопросов, где ответить нечем, отвечают все три, гладко и не опираясь ни на что. Решить, покрывает ли корпус вопрос, это не то же самое, что решить, покрывает ли его хоть кто-нибудь. Цифры и оговорки: [журнальная запись](experiments/2026-08-25_the-gate-that-fires-and-the-refusal-that.md).

### Ось темы: отказаться вместо похода наружу

Покрытие и тема это разные вопросы, и прогон выше отвечает только на первый. `agent.topic_threshold` добавляет второй: расстояние от вопроса до ближайшего чанка корпуса, посчитанное до того, как агенту предложен хоть один тул. Выше порога вопрос считается не нашим (порог свой на язык, сейчас 0.4560 для русского и 0.4374 для английского): внешние тулы не допускаются, найденное выбрасывается, и прогон отвечает отказом. Замер на тех же пулах: отказы на сотне off-domain растут с 11 до 50 (p<0.001), ложные отказы на корпусных парафразах остаются 0 из 100. Оба ограничителя были записаны до прогона. Цена видна не на парафразах, а на ручных вопросах, и она есть.

Порог объявляется **на язык**, потому что ось это расстояние до **нашего** корпуса, и насколько далеко ложится вопрос не по теме, зависит от того, делит ли он с корпусом лексику. Корпус почти весь английский, поэтому внекорпусный английский вопрос лежит от него на медиане 0.4547 против 0.5116 у русского, и одно число не может быть верным для обоих.

Выведено заново в августе 2026 на 1643 корпусных и 231 внекорпусном вопросе при бюджете ложных отказов 1%. Бюджет там из-за формы кривой, а не из вкуса: первый процент покупает 33 и 39 пойманных за 6 и 7 ошибочно отказанных вопросов, по пять с половиной за штуку, а второй покупает английскому 8 пойманных за 9 отказанных, а русскому вообще ничего. Два распределения перекрываются тонкой полосой: внутри неё порог режет тело внекорпусного распределения и лишь крайний хвост корпусного, а за ней каждый шаг стоит больше настоящих вопросов, чем спасает чужих.

Колено оценено по шести-семи вопросам, то есть числа подогнаны под ту выборку, на которой читаются. Выбор на половине A и отчёт на половине B показывают, сколько из этого переживает проверку: улов да, 84% по-русски и 73% по-английски, и на этом бюджете цена тоже, 1.42% и 0.47% ложных отказов на невиданных половинах. На бюджете 2% цена проверку не пережила: русская половина вернулась с 2.61%. Бюджет это цель с погрешностью около процентного пункта, и выкупить эту погрешность обратно тоже входит в цену первого процента.

Язык, которого никто не мерил, получает самый мягкий из объявленных порогов: гейт отказывает только там, где показано, что отказ не стоит настоящего вопроса. В снимок строки едет и применённый порог, и породившая его политика, а сравнение сверяет политику.

Интереснее та половина, которая не работает. Отлов это 11 → 49 из 83 на далёких темах (кулинария, химия, право) и 0 → 1 из 17 на легаси-стеках и пост-cutoff технологиях: для метрики расстояния FoxPro и Postgres это одна тема. Такие вопросы не вне темы, они внутри темы и вне корпуса, то есть это покрытие плюс свежесть, и лечится другим механизмом. Цифры, правила вето и порог, который сначала не мерил вообще ничего: [журнальная запись](experiments/2026-08-25_a-refusal-at-last-and-the.md).

### Гигиена корпуса: нарезка это параметр, а не данность

Вариант корпуса это именованная нарезка тех же источников, живущая рядом с остальными, со своим частичным векторным индексом и своей политикой в каждом снапшоте прогона. В `config.yaml` объявлены два:

| вариант | резчик | зачем он |
|---|---|---|
| `baseline` | `legacy` | заморожен: та нарезка, на которой корпус мерили впервые, никогда не переиндексируется |
| `clean_1024` | `rooted` | тот же рез по размеру, но путь заголовков берётся из объявленного корня, frontmatter разобран, мусор выброшен. Изолирует гигиену источников от смены сплиттера |

Варианты, которые померили и сняли, убраны и из файла, и из таблицы: `prefix_1024` (подзаголовки раньше размера), `cap_2048` и `noboiler_1024`. Их политики лежат в записях журнала, которые их измеряли, так что любой восстанавливается одной джобой, а вариант, который никто не отдаёт, перестаёт платить в план запроса всех остальных.

Политика несёт всё правило целиком, поэтому вариант получает ровно ту нарезку, которую просит: `chunker` (`legacy`, `rooted` или `structured`), `max_chunk_size`, `ceiling_on` (потолок считается по телу или вместе с префиксом) и `drop_boilerplate` (по умолчанию выключен: блок, повторяющийся дословно в половине файлов источника, выбрасывается, если он не единственный носитель своей секции, а раз это меняет нарезку, то это отдельный вариант, а не переключатель под существующим), типизированные с `extra: forbid`, чтобы ключ, который никто не читает, ронял старт, а не читался как переключатель. `header_prefix` выводится из `chunker`, а не объявляется: два ключа, решающие одно, так и разъехались. Ничего не выбрасывается, не разбирается и не префиксуется без указания политики, а preflight перенарезает каждый проиндексированный вариант и сверяет **текст** каждого чанка с тем, что лежит в таблице: источник, у которого нарезка поменялась, вполне может сохранить прежнее число строк.

`baseline → clean_1024` на 823 вопросах даёт **+0.0435 MRR по разделу** по всему набору, все шесть интервалов не задевают ноль; на предрегистрированной половине отчёта это **+0.0494**. `clean_1024 → prefix_1024` на тех же вопросах даёт **−0.0109 [−0.0253, +0.0032]**: на половине, где выбирается победитель, победителя нет, поэтому третий уровень заголовков ничего не купил и был удалён.

### Насколько глубоко обходится индекс, и почему это не число

`ef_search` прибит к 100, а `auto` это альтернатива, против которой его прибивали: самая глубокая ступень `ef_ladder`, план которой ещё содержит `Index Scan`, и спрашивается она у планировщика, а не вспоминается. Место, где планировщик бросает обход, двигается вместе с тем, что проиндексировано: добавление варианта сдвинуло точку примерно с 197 на 265, удаление не сдвинуло её обратно вовсе (`DELETE` оставляет страницы на месте), а вариант с меньшим числом строк получает ответ глубже, чем соседи по той же таблице. Глубина, зависящая от того, что ещё лежит рядом, невоспроизводима между днями, поэтому число лежит в файле.

Прибивание безопасно, а не слепо, потому что аудит проверяет **прибитое** число, а не только разрешённое: preflight спрашивает планировщик, ходит ли эта глубина по индексу, на **каждом проиндексированном варианте**, и отказывает, если хоть один уходит в сортировку. Это и случилось в тот же день, когда глубину прибили впервые. Прибили к 200 при трёх проиндексированных вариантах; удаление проигравшего и перезапись таблицы сдвинули перелом примерно с 248 на 123, 200 перестала ходить по индексу, preflight об этом сказал, и пин переехал на 100. Перезапись заодно перестроила hnsw-графы, поэтому мелкая ступень вышла дешевле, чем прежде была глубокая: на 100 парная дельта MRR по разделу против точного поиска теперь +0.0000 [0.0000, 0.0000], потерь нет, recall@20 1.0 (823 вопроса, `clean_1024`), тогда как до перезаписи та же ступень читалась +0.0011 с одним потерянным вопросом. При `auto` разрешённый ответ кешируется по двум статистикам, которые читает сам планировщик (`relpages`, `reltuples`). `ef_search` в запросе, в прогоне или осью сравнения перекрывает файл в обоих случаях; в снапшот прогона едет число.

Сравнение нарезок это эксперимент другого типа, а не вторая сущность. `POST /v1/experiment` с `kind: retrieval` принимает `axes` вместо одного свипаемого параметра (`{"variant": ["baseline", "clean_1024"], "rerank_top": [0, 20]}`), меряет каждую точку сетки на одних и тех же зафиксированных вопросах и для каждой руки считает парную дельту MRR против той руки, которая отличается от неё **только осью отчёта**, с бутстрап-интервалом. Стоит минуты и не требует ни карты, ни судьи: читается, куда попал правильный чанк, а не что сказала про него модель. Процедура едет в результате целиком и по рукам, в тех же полях, что пишет отдельный отчёт: вариант и набор, поиск и его глубина, размеры пулов, порог, настройки ключевой ноги, вопросы и их хеш, политика нарезки и отпечаток корпуса. Поэтому «эти двое несравнимы» это поле записи, а не строка в терминале, которую видел один человек.

Хорошо ли нарезан источник, спрашивается без эмбеддингов и без размеченных вопросов: `POST /v1/source/{id}/analyze` считает отчёт покрытия по одному тексту (доля чанков под настоящим заголовком, префикс тяжелее тела, дубли внутри файла и внутри источника, бойлерплейт, стоящий в большинстве файлов, огрызки, символьный суп, код без прозы и то, как часто границу поставил счётчик, а не структура автора), гейтит его, считает балл 0-100 и держит историю на вариант в `data_sources`. `GET /v1/source/{id}/report` читает эту историю обратно, а `GET /v1/source/compare` ставит две нарезки каждого источника рядом и считает те, у которых вердикт сдвинулся: так перенарезка оценивается до того, как ей задан хоть один вопрос. Метрика, которой нечего мерить, воздерживается вместо нуля: ноль проходит гейт и начисляет себе полный вес.

### Две реализации одного агента и две убранные

Поток выше начинался самописной петлёй: свой счётчик хопов, свой диспетчер, гейт покрытия вшит между ходами. Теперь его исполняет граф, а параметр `orchestrator` выбирает реализацию тех же политик. Обе заполняют один и тот же `AgentResult`, поэтому логирование, судья и метрики их не различают.

| `orchestrator` | реализация | что применяет |
|---|---|---|
| `langgraph_ported` (по умолчанию) | `StateGraph`, `app/orchestrators/graph.py` | всё |
| `langgraph_idiomatic` | голый `create_agent`, `app/orchestrators/react.py` | допуск тулов и ось темы (они отрабатывают до ветвления), без гейта покрытия, выброса контекста, уведомления о фолбэке, нуджа и финального хода без тулов |

Две реализации убраны, и каждая только после того, как была замерена против оставшейся: самописная петля и рука, выражавшая наши политики штатными хуками фреймворка. Обе совпали с графом в пределах собственного шума стенда по каждому ключу, который читает пайплайн, а вторая реализация поведения, уже закреплённого тестами, не даёт ничего и стоит ветвления в каждом будущем изменении. Их прогоны остались читаемыми в логе под `orchestrator=agent` и `orchestrator=langgraph_middleware`, запросить ни то ни другое новый прогон не может. Цифры: [запись](experiments/2026-08-26_the-same-agent-written-four-ways.md).

Картинка графа генерируется из скомпилированного графа скриптом `scripts/graph_to_d2.py`, и CI падает, если закоммиченная схема разошлась с кодом.

`/v1/question-log?orchestrator=langgraph_ported` режет логи по реализации, так же как это делают `fallback_policy` и `fallback_reason`. Значение `agent` там читается и больше нигде: запросить убранную петлю прогон не может.

Сами политики лежат в `app/use_cases/agent_policy.py` обычными функциями, и обе реализации с политиками зовут одни и те же. Отличается обвязка, в этом и смысл: вопрос «сколько стоит стандарт» становится измеримым, а не вкусовым. Две вещи не переживают переход на стандартный контракт тула, и обе записаны, а не спрятаны: виды ошибок (`timeout`, `auth`, `tool`, ...) схлопываются в «успех или ошибка», а у голой ветки нет финального хода, поэтому вопрос, которому нужен пятый хоп, заканчивается без ответа вместо отказа.

Две детали реализации, которые стоит украсть. При `corpus_first` придержанные внешние тулы надо отклонять на диспетчере, а не просто прятать от модели: штатный узел тулов собирается один раз из полного списка, поэтому сужение того, что видит модель, не мешает выполнить придуманный ею вызов. И уведомление о фолбэке едет в результате тула, а не системным сообщением, по причине с шаблоном, описанной выше.

## Как это устроено

- `app/config.py` - loader `config.yaml`.
- `app/orm/` - SQLAlchemy: `base` (declarative), `sync_db` (psycopg), `async_db` (asyncpg).
- `app/models/` - ORM-модели: `registry` (Model/ModelRole/Prompt), `eval` (Question/QuestionLog), `jobs` (Job), `corpus` (DataSource/DataChunk), `experiment` (Experiment + стейт-машина), `mcp_integration` (реестр внешних тулов).
- `app/llm.py` - клиент Ollama через OpenAI SDK (генерация / эмбеддинги / structured output) + резолвер роль→модель.
- `app/rerank.py` - cross-encoder реранкер (sentence-transformers, ленивая загрузка, по умолчанию на карте, и прогон отказывается идти, если находит его на процессоре).
- `app/job_queue.py`, `app/worker.py`, `app/job_handlers/` - очередь на Postgres (FOR UPDATE SKIP LOCKED) и воркер с ретраями/дефёром; хендлеры разнесены по тематике.
- `app/bootstrap.py` - idempotent-инициализация на старте.
- `app/sources/` - per-source ingestion (reader-паттерн: `Base` ABC + источники).
- `app/ingest.py` - резчик: заголовки находит `MarkdownHeaderTextSplitter`, текст режется из самого файла, секция делится по подзаголовкам раньше, чем по размеру, огрызки склеиваются, и то, что решило границу, пишется на чанк.
- `app/use_cases/ingest_quality.py` - отчёт покрытия: метрики по одному тексту, без эмбеддингов и без размеченных вопросов, гейтится на источник и хранится историей на `data_sources`.
- `app/db.py` - гибридный поиск (сырой SQL: pgvector `<=>`, FTS, ltree, RRF).
- `app/use_cases/` - `chat` (retrieve/answer), `agent` (политики, логирование и снапшот вокруг прогона агента), `agent_policy` (сами политики обычными функциями), `index` (сбор корпуса), `judge` (оценка ответа), `experiment` (агрегатор серии + RRF-композит), `retrieval_compare` (решётка рук, парные дельты и половины), `rejudge` (пересуд уже существующих ответов), `search_depth` (резолв и кеш глубины индекса), `mcp_integration` (внешние тулы).
- `app/orchestrators/` - адаптеры к фреймворку: `graph` (StateGraph), `react` (голый `create_agent`). Ни одного импорта langchain в `use_cases`.
- `app/agent_tools.py` - реестр тулов + `dispatch` + тул `search_corpus` поверх гибридного поиска.
- `app/mcp_server.py` - FastMCP-сервер (примонтирован на `/mcp`): тулы `search_corpus` / `answer_question` / `list_categories` поверх примитивов поиска.
- `app/mcp_ops.py` - ops MCP-сервер (примонтирован на `/mcp-ops`): `run_metrics` / `compare_runs` / `compare_pools` / `list_jobs` / `cancel_job` поверх eval-платформы.
- `app/evals/pools.py`, `app/evals/compare.py` - одно место, которое решает, в какой пул попал вопрос и чем закончился прогон: им пользуются метрики, сравнительный отчёт и оба MCP-инструмента.
- `app/api/` - REST-адаптеры (health + v1: chat / agent / categories / model / role / source / prompt / eval / experiment / questions / question-log / job).
- `app/seed.py`, `app/console.py` - сид промптов/банка вопросов; REPL-консоль.
- `app/evals/` - eval-стенд (runner + метрики retrieval + generation через judge).
- `tests/` - unit-тесты (чистая логика, без DB/Ollama): `docker compose exec rag-lab pytest -q`.

## Статус

Учебный проект: цель - освоить RAG/LLM-инженерию руками, из примитивов, а там, где у индустрии есть стандарт, перейти на него и замерить цену перехода. RAG из примитивов (гибрид, ltree, FTS) + FastAPI-сервер + 5-осевой eval-стенд на LLM-judge + production-слой (pyproject/uv, централизованный config, SQLAlchemy ORM sync+async, OpenAI-совместимый клиент, role-keyed lifecycle моделей, версионирование промптов, async job-queue, банк вопросов, reranking, route-driven eval-платформа, MCP-сервер).
